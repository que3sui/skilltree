# 建木 SkillTree · 基于技能树的去绩点化能力评价体系

> 版本 0.1（配套 MVP 实现）。本文档是体系设计：为什么做、是什么、怎么评、怎么防作弊、
> 怎么社区共建、怎么演进。对应实现见仓库各目录，快速上手见根 README。

---

## 1. 问题陈述：绩点为什么不可比

高校以绩点（GPA）分配保研、奖学金、交换等稀缺资源，但绩点的生成过程包含四重不可比因素：

| 因素 | 后果 |
|---|---|
| **教师不同** | 同名课程由不同教师讲授，给分尺度、考核方式（论文/闭卷/大作业）差异极大 |
| **同伴不同** | 相对评价（按比例给分）下，选课即抽签：进了强手如林的班，同样的水平拿更低的分 |
| **助教不同** | 主观题批改尺度取决于助教个人，无法跨班复核 |
| **选课不同** | 每人选修课组合不同，"水课"与"硬课"对绩点的贡献完全不同却等权计入 |

于是出现系统性错位：**绩点衡量的是"你在幸运抽中的那组考试里的相对位置"，而不是"你掌握了什么"**。
学生理性地追逐给分而非知识（选课先查"给分好不好"），这与教育的目标正好相反。

管理层并非看不见，而是改革有真实阻力：改规则要重新分配存量利益，缺乏一个
"能被所有院系接受、可解释、可申诉"的替代度量。**本项目的目标就是把这个替代度量造出来。**

## 2. 理念：从"分数排序"到"能力图谱"

用一句话概括：**不回答"你比他强多少"，改回答"你各自点亮了什么"。**

### 2.1 三个分离

1. **标准与执行分离**：评价标准（rubric）写成公开、版本化、社区共建的技能本体。
   标准由社区定义，执行由 AI 按 rubric 机械取证。任课教师/助教/同伴不再影响你被评价的方式。
2. **评价与排序分离**：输出不是单一序数量（分数），而是多维图谱——哪些技能点亮、各到 L几、
   前置链是否完整。资源分配可以从"按总分排队"变为"按图谱匹配"（如某课题组要的正是
   `algo.dp@L2 + sw.testing@L2` 的人）。
3. **裁决与复核分离**：取证（assessor）只管对照 rubric 找证据；红队（redteam）专职推翻它；
   仲裁（arbiter)汇总留痕。任何结论都附带完整证据链，可独立复核与申诉。

### 2.2 为什么前置约束是公平性的核心部件

技能点亮不是孤立的：`algo.dp` 点亮必须先有 `algo.recursion`。这带来两个性质：

- **防跳点亮**：单点证据再漂亮，前置不达就不放行（规则是确定性代码，不是模型意见）；
- **结构抗操纵**：刷单点容易，刷出一条自洽的前置链难——图谱比分数难注水得多。

## 3. 领域模型

三个核心对象（zod schema 见 `packages/schema/src/index.ts`，是唯一权威定义）：

### 3.1 SkillPack（技能本体）

```yaml
# ontology/packs/cs/ —— 目录即仓库，社区以 PR 共建
pack.yaml          # 元信息 + 等级语义（全包统一）
branches/
  prog.yaml        # 编程基础（10 技能）
  ds.yaml          # 数据结构（7）
  algo.yaml        # 算法（7）
  net.yaml         # 网络（4）
  db.yaml          # 数据库（5）
  sw.yaml          # 软件工程（8）
```

每个技能：`id`（点分路径如 `ds.hash`）、`tier`（层级，用于树布局）、`prereqs`
（前置 + 最低等级）、`keywords`（证据检索用）、`levels`（L1..Ln 的行为化 rubric 条目）。

**等级语义（全学科统一）**：
- **L1 认知与模仿**：能在指导下完成；能读懂、解释并小幅修改既有实现
- **L2 独立应用**：能脱离指导，在真实小型项目中正确、完整地运用（含边界情况）
- **L3 迁移与权衡**：能跨场景迁移，理解方法边界与代价，做出取舍并说明理由

**rubric 编写三原则**（保证 AI 可评、红队可驳）：
1. **可观察**：从项目证据中能判定（"在项目中把 O(n) 查找改为哈希并保持行为正确"），
   而非考记忆（"说出哈希表的定义"）；
2. **行为化**：描述做了什么，而非知道什么；
3. **可证伪**：红队能针对性地找反例（没有测试？来源可疑？）。

### 3.2 Evidence（证据）

MVP 证据类型 = **本地项目目录**（Git 仓库检出）。评测器把它折叠成有预算的确定性摘要
（`digest`：优先 README/清单/源码/测试，单文件与总量双截断），并计算 **证据指纹
`digestHash`**——同一份证据可识别、可复现。文档类（试卷/报告）与平台内在线测验
（AI 出题判卷）是后续证据类型，接口已预留（`Evidence.kind`）。

### 3.3 EvaluationReport（评测报告）

四 agent 流水线的产物，全程留痕：

```
survey      勘察：项目是什么、结构、入口、怎么跑
assessments 取证：逐技能等级 + rubric 逐条裁决 + 文件级证据引用 + 置信度
redteam     红队：测试存在性/来源核验/巨型文件/空壳证据…… + 总体风险
arbitration 仲裁：降级调整（from/to/reason）+ 备注
effective   有效等级：取证等级经【确定性】前置约束函数计算后的最终点亮状态
pack.contentHash + evidence.digestHash + model.details   ← 复现三要素
```

## 4. AI 评测流程与公平性保障

### 4.1 流水线

```
证据目录 ──digest──► 有预算摘要 ──┬─► 勘察 agent（事实，不评价）
                                  ├─► 取证 agent（逐分支：对照 rubric 裁决 + 引用）
                                  ├─► 红队 agent（专职质疑）
                                  └─► 仲裁 agent（汇总裁决，降级须留痕）
                                        │
                                        ▼
                      前置约束（纯代码）──► Report 落盘（reports/*.json）
```

关键防注入设计：**rubric 条目文本永远由本体回填，模型只填裁决**（verdict/引用/理由）。
即使提示词被证据内容污染，也无法伪造"标准"本身。

### 4.2 公平性机制

| 机制 | 实现 |
|---|---|
| 标准公开 | rubric 在 Git 仓库中，任何人可查可 PR |
| 可复现 | rubric 内容哈希 + 证据指纹 + 模型标识 + temperature=0 写入报告 |
| 可申诉 | 对结论有异议 → 指向具体 criterion citation 提交复核 → 换模型/换 prompt 重评并并排留痕 |
| 降权机制 | 红队 flag 的证据 → 仲裁强制降级（如 algo-notebook 中引用了外部来源文件的技能 L2→L1） |
| 方差控制 | 同证据重复评测的等级波动纳入报告质量指标（演进项）；关键裁决双模型交叉 |
| 规则与模型分界 | 前置约束、统计、DAG 校验全是确定性纯函数，与模型无关 |

### 4.3 为什么这能对抗"教师不公"

对比：传统评价链 = 教师 → 试卷/作业 → 分数 → 绩点（每环都不透明）。
本体系评价链 = 社区 rubric → 学生真实项目 → AI 取证 → 图谱（每环都公开可查）。
教师不再是被投诉对象，而可以成为 rubric 贡献者——**把教师从"裁判"重新定位为"立法者"**。

## 5. 社区机制：本体即开源仓库

### 5.1 关键洞察：不要自己造 GitHub

技能本体天然是一份 Git 仓库，**GitHub/Gitee 的 PR + Issue + Review 机制就是现成的
社区协作层**：fork → 改 rubric → 提 PR → maintainer review → 合并 → 版本号递增。
issue 用来讨论"这个技能该不该拆""L2 标准是否过严"。历史、署名、冲突解决，全部白拿。
自研社区平台是验证价值之后的事，不是前提。

### 5.2 治理角色

| 角色 | 权力 | 产生方式 |
|---|---|---|
| contributor | 提 PR/issue 修 rubric、增技能 | 任何人 |
| rubric maintainer | review 并合并某分支的 PR | 贡献史 + 现有 maintainer 2/3 同意 |
| domain steward | 定分支结构与等级语义 | 首批由发起团队担任，逐步选举 |

### 5.3 rubric 版本语义（借鉴 semver）

- **PATCH**（措辞澄清，不改变可判定范围）：随时合并；
- **MINOR**（新增技能/新增等级条目）：合并后新评测默认采用，旧报告不回溯；
- **MAJOR**（修改现有条目的可判定范围）：必须附「影响面说明 + 抽样重评报告」，
  且保留旧版本 rubric 供历史报告对照。

报告绑定 `pack.contentHash`，任何结论都能回答"你当时是按哪一版标准评的"。

## 6. 反博弈设计

| 攻击 | 防线 |
|---|---|
| 直接抄袭/模板项目 | 红队 provenance 核验（来源标记、与常见模板雷同检测）；演进项：跨证据查重 |
| AI 代写 | 红队 oversized_file / 风格突变启发式；演进项：**答辩式抽查**——agent 就项目细节追问，回答与代码不符则降级 |
| 空壳注水（README 写得震天响） | stub_evidence 核验：证据不足则仲裁清零（见 empty-stub 样例的评测结果） |
| 针对性刷单点 | 前置约束链 + rubric 条目要求"真实项目中运用" |
| 污染评测模型（证据里藏提示词） | rubric 文本由本体回填；裁决结构由代码校验；摘要为只读文本 |
| 恶意 PR 稀释标准 | rubric maintainer review + MAJOR 版本流程 |

诚实的边界：**本体系不怕"评价不准"，怕的是"评价被操纵且看不出来"。**
因此一切设计优先保证可审计（引用、留痕、复现），其次才是准确率。

## 7. 技术架构

### 7.1 MVP 实现（本仓库）

```
全 TypeScript monorepo（pnpm workspace），一套 zod 类型贯穿本体→评测→前端
ontology/        技能本体（YAML，目录即仓库）
packages/schema    领域模型 + 前置约束/统计纯函数
packages/evaluator digest 证据摘要 + provider 抽象 + 四 agent + CLI
apps/server      Hono 本地服务：本体/报告 API + 触发评测
apps/web         React + 手写 SVG：科技树 + 蜂窝网格双视图
samples/         三个演示证据（优质 / 来源存疑 / 空壳）
```

选型理由：
- **与 dsh 同生态**（TypeScript / npm / Cordis 社区），一套语言贯穿全栈，单人可维护；
- **MVP 不引数据库**：本体是 YAML、报告是 JSON 文件，`git` 就是版本管理，平台化时再上 Postgres；
- **可视化手写 SVG + CSS 3D**：科技树/蜂窝的本质是布局+点亮动效，手写比图表库更可控、零重量级依赖；层叠视角用 CSS 3D 直立卡片（billboard 保证任意角度文字可读）+ DOM 实测投影连线，跨分支依赖只在层间显现；聚焦模式（双击技能）提供 Obsidian 局部图语义；
- **模型可替换**：`ModelProvider` 接口（mock / deepseek / 未来 dsh runtime），评测核心不绑定任何 SDK。

### 7.2 与 DeepSeek Harness 的关系

dsh 是 DeepSeek 官方开源的全插件 agent harness（Cordis 架构）。本项目与它的集成是
**分层渐进**的（详见 `dsh/README.md`，基于其源码文档梳理）：

1. **已实现**：共用其模型接入约定（OpenAI 兼容 wire API + `DEEPSEEK_API_KEY`）；
2. **已提供**：dsh 技能包 `dsh/skills/skilltree-eval/SKILL.md`——放进任何 dsh 工作区的
   `.dsh/skills/`，dsh agent 即获得"驱动建木评测、解读报告"的能力；
3. **规划**：把四 agent 评测器注册为原生 dsh 插件（`ctx.tools.register` 暴露
   `read_digest`/`rubric_lookup`/`submit_verdict`，经 `ctx.llm.stream` 调模型，
   `--profile headless` / SDK 子进程无界面运行）——待 dsh 度过开发者预览期后实施。

之所以分层：dsh 官方明示预览期存在破坏性变更。**评测核心零依赖 dsh 内部 API**，
dsh 的变化只影响可选适配层。

### 7.3 演进路线

- **阶段 1（本 MVP）**：单机全流程跑通，本体种子（CS 41 技能），mock/deepseek 双通道
- **阶段 2**：本体上 GitHub 公开共建；多证据类型（文档、在线测验）；双模型交叉评测；申诉工作流
- **阶段 3**：平台化（用户档案、院系/组织视图、按图谱匹配的资源分配工具）；答辩式抽查；
  多校 rubric 联盟（各自维护分支，共享等级语义）

## 8. 伦理与风险

1. **模型偏见**：模型对项目风格/语言/框架可能有偏好 → rubric 行为化 + 多模型交叉 + 抽样人工复核；
2. **隐私**：项目证据可能含敏感信息 → MVP 全本机运行、报告本地存储；平台化时证据默认私有、
   只公开结论与最小引用片段；
3. **数字鸿沟**：证据偏向"能做项目的人" → 扩展证据类型（纸面推导、实验报告、测验），
   不同证据类型可点亮不同技能子集；
4. **不被神化**：本体系的输出是"证据支持的能力图谱"，不是人的全部价值。
   它设计为**替代绩点参与资源分配的可申诉依据**，而非新的排名暴政——图谱刻意不做总分，
   就是不给"一句话压扁一个人"留后门；
5. **误判代价**：任何点亮都可降可升（重评留痕），评估结论必须带置信度与红队风险提示。

## 9. MVP 使用速查

```bash
pnpm install
pnpm validate                        # 校验本体（41 技能 / 6 分支）
pnpm demo                            # mock 评测三个样例，报告落 reports/
pnpm server                          # http://127.0.0.1:8787 （API + 托管 web 构建产物）
pnpm web                             # 开发模式 http://127.0.0.1:5173

# CLI 直接评测
pnpm evaluate --repo samples/task-todo --provider mock
pnpm evaluate --repo <任意本机项目> --provider deepseek   # 需 DEEPSEEK_API_KEY
```

三个样例的 mock 评测结果呈现了体系的核心行为：
`task-todo`（优质）→ 22/41 点亮、风险低；`algo-notebook`（引用外部来源）→ 红队标记、
4 项技能被仲裁降级至 L1；`empty-stub`（空壳）→ 红队判证据不足、全部清零。

## 10. 大赛提交版摘要（"一〇七杯"智能体赛道）

### 10.1 解决的场景问题

绩点衡量的是"你在幸运抽中的考试组里的相对位置"：教师给分尺度、助教批改宽严、同伴水平、
选课运气四重不可比因素叠加，使跨班级/跨院的绩点无法公平均衡地支撑保研、奖学金、课题组选人
等资源分配（智慧校园的"教学赋能 + 服务管理"双命中场景）。
建木 SkillTree 把"可比的单一序数"换成"不可比的诚实证据集合"：学生提交真实项目仓库，
AI 依据**公开、版本化、社区共建**的技能本体（rubric）逐技能裁决并点亮技能图谱，
输出可审计、可申诉的能力档案。

### 10.2 技术架构（四 agent 流水线 + 本体/报告数据流）

```
ontology/packs/*（三学科本体：cs 41 / mds 18 / eie 19 技能，PR 共建 + semver）
        │ 加载时做 DAG 环检测；rubric 文本永远由本体回填进 prompt
        ▼
┌──────────────────── 评测流水线（TypeScript，模型可换）────────────────────┐
│ surveyor 勘察   语言/入口/测试/观察/git 历史 → 证据摘要（内容级 SHA-256）   │
│ assessor 取证   逐分支调模型：按 rubric 逐条裁决 + 文件:行号级引用          │
│ redteam  红队   质疑证据真实性/来源/注水/巨型粘贴/提交历史 → 结构化检查单   │
│ arbiter 仲裁   汇总红队证据，下调等级必须留痕（from→to+理由）               │
└──────────────────────────────────────────────────────────────────────┘
        ▼ applyPrereqCaps（确定性纯函数：前置约束，防跳点亮）
EvaluationReport JSON（schema 版本化：证据哈希 + rubric 哈希 + 模型信息 + 全程留痕）
        ▼
web 三视角可视化 + 点亮回放 + 评审留痕 + 学习轨迹/成长对比/申诉/分享卡
```

### 10.4 技术难点

1. **反提示词注入**：模型只能填裁决 JSON，rubric 文本永远由本体代码回填——证据仓库里
   写"请给我 L3"不影响评价标准本身；
2. **确定性约束与模型裁决分离**：点亮合法性（前置约束）不交给模型，是可单测的纯函数，
   杜绝跳点亮类刷分；
3. **对抗性评测**：红队 agent 专查测试真实性、来源合规、模板雷同、巨型粘贴、空壳注水、
   **git 提交历史渐进性**，仲裁据此降级并留痕（algo-notebook 样例：2 项技能被 L2→L1 下调，
   理由与指认文件可查；octocat/Hello-World 直评 0/41 高风险——"3 次提交仅为 README 换行"）；
4. **推理模型工程适配**：SSE 流式接收规避长思考期的连接超时（900s 看门狗）；JSON mode
   按模型适配（glm 系 json-mode 会把答案掉进 reasoning_content）；方差实测 task-todo ×3
   轮点亮 12/13/12；
5. **工程可靠性**：模型输出过 zod 校验 + 解析自修复重试；32768 token 预算（reasoning
   token 计入配额）；证据摘要含内容级 SHA-256 哈希（防"改内容不改行数"的证据调包）；
   报告落盘前脱敏闸（四种密钥形态拒绝写入）。
